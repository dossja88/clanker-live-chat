## Diagnosis boundary and discriminating evidence

**Confirmed failure stage:** after a GitHub PR comment is received, Jules's GitHub publication path produces a new bot-authored commit with the same file snapshot instead of an updated implementation. This happened across two independent tasks. The repeated original commit message points to a re-publication of the original change set, but is **not proof** which Jules subcomponent failed.

**Unresolved internal causes:** (A) Jules did not make edits despite processing feedback; (B) edits exist in Jules's task filesystem but were not staged/committed or were discarded; (C) a stale patch or checkout was republished despite other internal changes. Only the existing session's *activity logs, code diff panel, git status/staging output and publication logs* can distinguish A/B/C.

To finish provider-level root-cause diagnosis **without consuming a new task**, inspect both existing Jules tasks' activity/diff around review timestamps, especially #7200037830362515152. If source changes appear in the Jules diff panel but not GitHub, suspect staging/publishing. If no source changes appear, investigate whether feedback reached code execution at all. If activity shows a correct new patch but a push of the original SHA tree, investigate stale-export/publisher synchronization. Do not claim a confirmed cause without this evidence.

## Safe reuse-first mitigation

1. Do not reopen the two superseded PRs, reapply their `jules` labels, restart their tasks, or send further redundant review comments. Their useful work is already integrated.
2. For future *distinct authorized* Jules assignments, keep **one writer per Jules branch**. Give a small reviewer assertion while the original task's **in-task chat** is available, and check its task activity/diff before publishing. Google's Jules documentation supports interactive in-task feedback: https://jules.google/docs/running-tasks/ .
3. Require evidence *before* accepting a feedback response: exact prior/revised head, `git status --short`, `git diff --stat`, `git diff --cached --stat`, a **nonempty resulting code/test diff**, actual Node test output, and a resulting Git tree SHA distinct from the reviewed SHA. When needed, explicitly request `git add -- <scoped files>`, examine staged diff, then commit/push **only a genuine changed tree**. Never suggest `--allow-empty`, `git reset --hard` or force push as a fix.
4. In an offline local checkout with both refs fetched, run `node scripts/check-agent-feedback-diff.cjs --before <reviewed-head> --after <candidate-head>`: exit 0 for real path changes, 2 for **NO_CHANGE**, 1 for invalid refs/non-descendant/error. This is advisory, not a service, branch-protection setting, or CI workflow. `node tests/agent-feedback-diff.cjs` tested **7/7** real Node.js v22.16.0/Git v2.47.3 synthetic histories on 2026-10-22. A changed file is necessary, not sufficient: tests and semantic review remain mandatory.
5. On the first no-op after feedback, **stop treating the commit as implementation**. Inspect the Jules task's activity and staging/publishing; do not keep trying multiple identical PR comments or burn free tasks. If the activity log demonstrates an internal defect, use the existing Jules UI Feedback control to report the two task URLs and exact GitHub commit evidence: https://jules.google/docs/feedback/ . No report submission is claimed here.
