## First-pass quality and acceptance (cross-project owner standard, 2026-10-25)

- **Define success before substantial work.** State the intended user/audience, real use (feasibility, private review, client deliverable or public release), essential outcome, professional/reference quality where relevant, measurable acceptance criteria, and how the *actual result* can be inspected. Scale research to stakes; do not substitute assumptions for obtainable facts.
- **Preflight the critical path.** Verify required inputs, rights for that use, tool access, delivery/playback environment, cost, approvals and feasible QA before bulk production. Resolve a blocker with the smallest authorized feasibility test; if unresolved, hold downstream work rather than build a knowingly unusable substitute. Existing stronger security/privacy/spending/release rules prevail.
- **Make the first substantial attempt informed.** Aim for a genuinely useful review candidate, not a barely functional placeholder that obviously fails the goal. Choose methods based on fit for purpose, anticipate known failure modes, and compare with competent real-world examples where that can materially improve results.
- **Quality-assure the finished artifact from its audience's perspective.** Inspect/listen/play/run the real output (including relevant visual, audio, timing, content, accuracy, usability, platform and delivery-path requirements); test meaningful behavior and edge cases, not merely script exit codes, logs, file presence or synthetic mocks. Mark unavailable device/user validation as unverified.
- **Correct observable defects before owner review**, within existing approval and cost bounds. Do not make the owner the first line of QA for issues detectable internally. If the owner asks “does this achieve what we wanted?”, only answer *yes* when supported by the agreed acceptance evidence; otherwise state exactly what fails and resolve it where authorized.
- **Use honest completion labels:** *exploration* = feasibility only; *prototype* = selected capability only; *review candidate* = internal acceptance checks passed but subjective/owner review remains; *complete* = intended outcome and observable acceptance criteria verified, with applicable approvals retained. Technical completion alone does not prove client-ready quality or publication authority.
- **Keep QA proportionate.** Prefer targeted high-value fixes over repeated broad checks, unnecessary polishing, new fees/credits, or speculative additional artifacts. Report what passed, what was not tested, what remains gated, and the next meaningful action.

**Clanker-specific acceptance:** A live-host, Twitch/gameplay or cloud-autonomy milestone must show the real integrated end-to-end behavior (identity, connected platform, permissions, observability, safe recovery and target-device use), not only a GitHub Pages facade, green mocked tests or attractive character expressions. Keep proposed hosting separate from actually operating unattended.
